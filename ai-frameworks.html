Sample, Judge, Improve

Notes on a family of hand-rolled test-time sampling frameworks for LLMs — best-of-N selection, semantic majority voting, validator loops, and an elimination tournament where the losers don't get discarded. They get coached.

Context

This is a writeup of a set of experiments I built before "agentic" was the word for it — back when the API surface of an LLM was a chat completion and nothing else. No tool calling, no structured-output mode, no off-the-shelf orchestration frameworks. If you wanted a model to behave like a system rather than a chatbot, you composed raw completions yourself and parsed what came back.

So that's what I did. The result is a small family of sampling frameworks in Java, built on my own utility and client library (ogerutil), with zero external LLM dependencies. Each framework wraps the same primitive — generate N candidate completions, then reduce them to one — with a different reduction strategy, and each strategy encodes a different theory about where quality comes from.

I never ran these through a large-scale evaluation; that's stated up front and revisited honestly at the end. What this document covers is the part that I think is worth reading anyway: the design space, the architecture, the failure modes I anticipated and designed around, and the parts that made it into a real project.

@Section(kind = "core primitive")

The shape of the problem

A single LLM completion is a lottery ticket. Temperature gives you variance; variance means some samples are great and some are junk, and a one-shot caller just takes whatever comes out. The whole premise of test-time compute is that you can trade inference budget for output quality — buy several tickets, then spend a little more compute deciding which one to cash.

Every framework here is a different answer to the second half of that sentence. Selection can be a single judgment, a tournament, a vote, a checklist of validators, or — the most ambitious version — an iterative loop where candidates are not only ranked but revised.

One design decision is shared by all frameworks and worth stating once: the output is always a single, ordinary assistant message. Whatever tournament happened internally, the caller gets back something it can append to a chat history as if it were a normal completion. The frameworks are drop-in replacements for a single model call, which is exactly what made it trivial to slot one into a real application later.

@Framework(name = "SelectBest", status = "implemented", since = "April 2025")

SelectBestFramework

The baseline: generate N samples from a free-form prompt ("write a joke"), then run a selection phase with a second prompt ("select the best joke"). Generation and selection are decoupled — separate model, separate request settings — because they want different things. Generation wants a capable, high-temperature model; selection is a comparison task that a smaller, cheaper, low-temperature model can often handle, which matters when you're paying the selection cost over many samples.

The interesting design surface is how to reduce N samples to one. I implemented three modes behind a single ReduceSettings switch:

ALL_AT_ONCE puts every sample into one judging prompt. Direct comparison is the strongest signal a judge can have, but the context grows linearly with N, and past some point you're not judging samples anymore, you're testing the model's long-context recall. ONE_BY_ONE grades each sample in isolation against criteria — it scales to any N and reinforces objectivity, but the judge can never say "this one is better than that one," so the grading rubric in the prompt has to carry all the weight. ELIMINATION_BRACKET is the compromise: compare chunkSize samples at a time, tournament style, keeping direct comparison and small contexts at the cost of more selection calls and the constraint that N must be a power of the chunk size (which the config validation enforces up front, not at round three of a tournament).

The selection prompt is user-supplied but contract-checked: it must contain {{samples}} and {{format_instruction}} template slots, which the framework fills with XML-wrapped samples and mode-specific output instructions. Getting structured choices out of a model without tool calling is its own story — covered in the engineering notes.

@Framework(name = "MajorityVote", status = "implemented", builtOn = "SelectBest")

MajorityVoteFramework

Self-consistency — sample N times, take the majority answer — is one of the oldest reliable tricks for reasoning tasks. The classic version needs a parseable final answer so you can count votes mechanically. Mine doesn't: instead of counting strings, it hands all N samples to a judge with a fixed prompt to select the sample representing the most common train of thought.

That makes it a semantic majority vote. Two samples that reach the same conclusion through different wording still count toward the same cluster, and it works on free-form output — prose, plans, code — where there is no single token to extract and tally. Architecturally it's a thin specialization of SelectBestFramework: it synthesizes the reduction prompt (preserving the original system messages so the judge keeps the same framing as the generator), pins the mode to ALL_AT_ONCE, and optionally threads through an assistant prefill to steer the judge's output format. One framework expressed in about thirty lines on top of another — which was the point of building these as composable pieces rather than scripts.

@Framework(name = "Validator", status = "design study")

ValidatorFramework

The previous frameworks pick the best of what the lottery produced. This one asks a different question: what if you have hard requirements? The ValidatorFramework targets outputs that must pass a checklist of V independent validators, each phrased as a binary question with a user-controlled suggested fix ("is this a dad joke? if not, why?"). The loop:

  1. Generate N samples from the initial prompt P.
  2. Grade every sample against all V validators; each failed check attaches its fix to the sample.
  3. If any sample passes everything, return it — done.
  4. Otherwise feed each sample plus its accumulated fixes into a refinement prompt R, get N revised samples, and loop — up to I iterations.

The cost is O(N·V·I), and the documentation in the source spends most of its length on the failure mode that budget buys you: cyclic toggling. With too many validators, each refinement fixes one criterion and quietly breaks another that previously passed, and the loop oscillates forever. The design notes around this became the most interesting part of the framework — among them: always re-list passing validations during refinement so the model knows what not to break; give validations names (and let a model generate the name as its first structured output, since naming a check seems to sharpen the judgment of the check itself); run generation hot and validation cold; consider hiding the true goal from the initial prompt entirely to maximize diversity, then let validators steer; and treat fragile criteria as resample-only, never refine, because a refiner under pressure will happily make the minimal adversarial edit that tricks a validator without honoring its intent.

Two release valves are specified for when the loop doesn't converge: a topV parameter that keeps only the best-validated fraction of samples and replaces the rest with fresh generations (cheaper than refining a sample dragging an ever-growing list of issues), and a failure mode choosing between KEEP_BEST_ATTEMPT and EMPTY_HANDED when I iterations expire.

status This framework exists as a fully specified design — configuration surface, phase model, and a long backlog of parameter ideas in the source — rather than finished code. I'm including it because the failure analysis (toggling, adversarial refinement, validation throttling) is the part of the work I'd defend most strongly, and it directly shaped the frameworks that were finished.
@Framework(name = "ReverseElimination", status = "implemented", since = "April 2025")

ReverseEliminationFramework

This is the centerpiece, and the inversion in the name is the whole idea. A normal elimination tournament asks the judge to pick the best sample and discards the rest. This one asks the judge to pick the worst — because the loser is the sample we're about to do something with.

When a sample loses a match, the judge must also emit a structured critique of why it lost. That critique, born from direct comparison against a superior sample, is the highest-quality improvement signal available anywhere in the system — far better than asking a model "make this better" in a vacuum. The losing sample is sent to an improvement step that revises it against the critique, and then it gets a rematch. Only after maxLosses defeats is a sample actually eliminated and the winner advances. Rounds recurse, bracket-style, until one sample remains.

Two refinements keep the tournament honest. First, the rematch is a stability mechanism, not just a second chance: a winner has to beat the same opponent repeatedly, across minor perturbations, before its win counts — guarding against the single noisy judgment that plagues naive single-elimination. Second, an optional match shuffler reseeds rematches: instead of replaying the exact same pairing, losers are grouped by identical win/loss records and rotated among matches with comparable opponents, with the rotation constructed so no contestant can land back in its own seat. Fair matchmaking, derived from the standings.

The score semantics fork the framework's personality. With resetScoreAfterRound = false, losses are global, strong initial samples tend to carry through, and the run finishes fast. With true, every round wipes the slate — which means the weakest samples accumulate the most improvement steps, and a sample that started as junk can, in principle, be coached into the eventual winner. Whether that's a feature or a budget fire depends entirely on your prompt.

known risk · by design There is no mechanism guaranteeing a revision is an improvement. Revising samples is a double-edged sword: it can make good ideas great, or degrade a many-time winner into junk at the last moment. The documented mitigations live in the improvement prompt — ask for minor edits, restate the original goal so revisions can't drift off-theme over many iterations, and consider disabling shuffling for a stable arena within a round. A planned-but-unbuilt refinement: scale how much change is permitted by tournament progress, so late-round revisions become nearly conservative.

Everything is traced. A per-sample revision history records every version of every sample alongside its win/loss record and accumulated critiques, so after a run you can read exactly which critiques moved a sample forward and which revisions sent it sideways. That traceability is the honest selling point of the framework: even without formal evals, a run produces an inspectable record of what the judge rewards — which is precisely what you want while iterating on generation and selection prompts, before "locking them in" and switching back to the cheaper SelectBestFramework for production use.

@Planned("scratchpads of ideas")

Sketches: where the idea wants to go

Two further frameworks exist as design notes, and both fall out of pushing ReverseElimination to its logical limits.

EloFramework. If you keep granting losers rematches, you eventually lose the guaranteed exit condition — win-trading between samples could cycle forever, and rounds stop making sense because you can't promise fair pairings or equal match counts. At which point the honest conclusion is: stop pretending it's a bracket. It's a matchmaking system. Give every sample an Elo rating, let matches run until ratings settle, and return the top-rated sample. You trade a bounded runtime for the ability to fill any compute budget you have.

ConsensusFramework. Majority voting, but adversarial: samples don't just sit in a context waiting to be counted — each one steelmans itself and argues why it beats the others, and crucially, a sample may concede or alter itself to merge with a stronger position. The vote isn't taken over the initial population but over the population after negotiation. Intended for decision-making tasks where the goal is the right answer rather than the best artifact — majority vote on steroids.

@Section(kind = "the unglamorous parts")

Engineering notes

Structured output before structured output

Every judgment in these frameworks needs a machine-readable answer from a model that only emits prose. The convention: format instructions are injected into the user-supplied template, samples are wrapped in indexed XML (<sample index="3">), and the model is told to emit its verdict in tags — a <critique> with a summarized copy of why the loser lost (worded so it can be handed to the improver), then a <choice> containing the losing index. Parsing is defensive at every step: the tag must exist and be complete, the choice must parse as an integer, and it must be a member of the set of indices actually present in this match — a hallucinated index is rejected as InvalidChoice, not silently mapped to a contestant.

// the judge's contract, injected via {{format_instruction}}:
Always refer to the samples with their original index from the XML attribute.
After thinking, include a summarized *copy* of your critique of the losing
sample within a <critique></critique> tag (so that it can be improved).
Output the sample index of the losing sample within a <choice></choice> tag.

Feeding the exception back to the model

My favorite small idea in the codebase. When a parse fails — malformed tag, out-of-range index — the framework doesn't just blindly retry the identical prompt and hope the dice land differently. The retry splices the Java exception into the conversation as an additional user message ("during your previous evaluation, the following error occurred: …"), carefully re-ordering around any assistant prefill, and asks again. The model gets to see what it did wrong. Flagged as experimental in the source, but it's recognizably the same pattern that later became standard in agent loops: tool error in, corrected call out — implemented here against a bare chat-completion API because there was nothing else to implement it against.

Failure as a first-class parameter

A tournament is a long chain of network calls and fallible parses, and the right reaction to a failure depends on what failed. A lost improvement is non-critical — the unrevised sample can simply rematch as-is. A lost match verdict is structural and must be retried regardless, because the bracket can't proceed without it. So retry policy is a four-mode enum on the config (RETRY_OR_THROW, RETRY_OR_SKIP, SKIP_FAILURES, THROW_ON_FAILURE), and each call site declares whether it's critical. Configs are validated eagerly and loudly — template slots present, sample counts power-of-chunk-size, contradictory settings (an improvement model with no improvement prompt) rejected — because the worst place to discover a config error is three rounds and two hundred completions into a tournament.

Measuring whether the judge means it

For ONE_BY_ONE grading I prototyped a small statistical check on the scores themselves: a normalized standard deviation, scaled by a uniqueness factor that punishes degenerate distributions (a judge that answers "7" for everything), with Shannon entropy computed alongside for comparison. The motivating question: is the judge actually discriminating between samples, or rubber-stamping? If every sample scores within noise of every other, the reduction step is theater and the signal has to come from somewhere else. Exploratory, but it's the seed of judge-calibration tooling.

Everything composes

Generation, selection, and improvement each take their own model and request settings, because the phases want different things — and because a tournament's cost center is selection calls, where a small fast model is often enough once the prompts are stable. Thinking blocks are handled explicitly everywhere (include in judging or not; strip from final output; preserve through synthetic revision messages so a revised sample remains indistinguishable in shape from a generated one). And one disclosure made in the source itself, kept here in the same spirit: the match-shuffler helper was pair-programmed with an LLM — fitting, for a library whose entire purpose is putting models to work on models.

@Section(kind = "status & honesty")

Status, real use, and what I'd do differently

Straightforwardly: there are no benchmark results here. The frameworks were tested manually — enough to debug the machinery, watch tournaments resolve, and read revision histories — but never run through an evaluation at a scope where I'd stand behind quantitative claims. SelectBest, MajorityVote, and ReverseElimination are implemented and working; Validator is a fully specified design; Elo and Consensus are sketches. The writeup is honest about which is which, because the design reasoning is the part I'm presenting, not measured wins.

One piece did graduate into production use: the sampling core powers a separate project of mine — a multi-user chat where an LLM participates as one of the chatters — where it handles the core sample generation behind the persona's messages. The drop-in-replacement property paid off exactly as intended: to the rest of that application, the framework is just a function that returns one assistant message.

If I rebuilt this today, the structured-output layer would sit on native tool calling and JSON schemas instead of XML tag parsing, the exception-splicing retry would be a standard tool-error loop, and the first milestone would be an eval harness before a fourth framework — the revision histories were crying out to be aggregated into actual statistics. But the questions the frameworks encode haven't aged: where selection signal comes from, how to spend critique, when revision helps and when it corrodes, and how much structure a judgment needs before you can trust it. Those are the same questions every agent system is answering now — these were my answers from before the vocabulary existed.
